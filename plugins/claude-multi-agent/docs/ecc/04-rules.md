## 1. Rulesとは何か

Rulesとは、Claude Codeセッション中に**常時適用されるコーディング規約・ワークフロー定義**のことです。プロジェクトの `CLAUDE.md` やシステムプロンプトとは異なり、Rules は開発チーム・プロジェクトを横断して再利用可能な「共有知識ベース」として機能します。

### 主な役割

| 役割 | 説明 |
|------|------|
| **規約の強制** | コーディングスタイル・命名規則・ファイルサイズ上限などを一元管理 |
| **ワークフローの標準化** | 開発フロー・レビュー・コミット形式を統一 |
| **セキュリティゲート** | コミット前の必須チェックリストを自動で参照させる |
| **パフォーマンス最適化** | モデル選定戦略・コンテキスト管理の指針を提供 |

Rulesを適用するには、CLAUDE.mdから `@rules/common/*.md` や `@rules/typescript/*.md` 形式でインポートするか、フックと組み合わせて動的に参照させます。

## 3. 共通ルール（common/）詳細

### 3.1 agents.md

利用可能な組み込みエージェントを定義するファイルです。

**定義されているエージェント（9種）:**

| エージェント名 | 役割 |
|--------------|------|
| `planner` | PRD・アーキテクチャ・タスクリスト生成 |
| `architect` | システム設計・構造最適化 |
| `tdd-guide` | TDDフロー（RED→GREEN→IMPROVE）のガイド |
| `code-reviewer` | コードレビュー・品質チェック |
| `security-reviewer` | セキュリティ脆弱性分析 |
| `build-error-resolver` | ビルドエラーの診断・修正 |
| `e2e-runner` | E2Eテスト（Playwright）の実行 |
| `refactor-cleaner` | リファクタリング・コード整理 |
| `doc-updater` | ドキュメント更新・同期 |

**重要なルール:**
- 独立したタスクは必ず**並列実行**する（直列実行はアンチパターン）
- `split-role` サブエージェントパターンで多角的分析を行う

### 3.2 coding-style.md

コーディングスタイルの根本原則を定めるファイルです。以下はすべて **CRITICAL**（絶対遵守）扱いです。

#### イミュータビリティ
```
オブジェクトは常に新規作成する。既存オブジェクトのミューテーション（直接変更）は禁止。
```

スプレッド演算子・コピー関数を使用してイミュータブルな更新を行います。

#### ファイルサイズ制限

| 区分 | 行数 |
|------|------|
| 標準 | 200〜400行 |
| 上限 | 800行（絶対厳守） |

800行を超えそうな場合は、責務ごとにファイルを分割します。「小さなファイルを多数持つ」ことが推奨スタイルです。

#### エラーハンドリング
- 全レベル（関数・モジュール・アプリケーション）で包括的なエラー処理を実装する
- エラーを握りつぶす（silent fail）ことは禁止

#### 入力バリデーション
- システム境界（ユーザー入力・外部APIレスポンス）でスキーマベース検証を実施
- 内部関数間では過剰なバリデーションを避ける

#### ハードコード禁止
- マジックナンバー・文字列定数はすべて名前付き定数または環境変数に抽出する

### 3.3 development-workflow.md

開発の進め方を5フェーズで定義するファイルです。

```
Phase 1: Research & Reuse
Phase 2: Plan First
Phase 3: TDD Approach
Phase 4: Code Review
Phase 5: Commit & Push
```

#### Phase 1: Research & Reuse（必須）
実装前に必ず調査を行い、車輪の再発明を防ぎます。
- GitHub検索でスケルトンプロジェクトを探す
- Exa MCP で最新のプラクティスを調査
- パッケージレジストリで既存ライブラリを確認

#### Phase 2: Plan First
`planner` エージェントを使い、以下を事前に生成します。
- PRD（製品要件定義）
- アーキテクチャ設計
- タスクリスト

#### Phase 3: TDD Approach
**テストを先に書く**ことが必須です。
1. テスト作成（失敗状態 = RED）
2. 実装（成功状態 = GREEN）
3. リファクタリング（IMPROVE）

#### Phase 4: Code Review
`code-reviewer` エージェントで実装直後に即時レビューを行います。セルフレビューと組み合わせてもよいです。

#### Phase 5: Commit & Push
- Conventional Commits 形式で詳細なメッセージを書く
- コミット前セキュリティチェックを必ず実施（→ [security.md](#38-securitymd) 参照）

### 3.4 git-workflow.md

Git操作の規約を定めるファイルです。

#### コミットメッセージ形式

```
<type>: <description>
```

**利用可能なtype一覧:**

| type | 用途 |
|------|------|
| `feat` | 新機能追加 |
| `fix` | バグ修正 |
| `refactor` | リファクタリング（機能変更なし） |
| `docs` | ドキュメントのみの変更 |
| `test` | テスト追加・修正 |
| `chore` | ビルドツール・依存関係の更新 |
| `perf` | パフォーマンス改善 |
| `ci` | CI/CD設定の変更 |

#### PRワークフロー
PRレビュー前に以下のコマンドで完全な差分を確認します。

```bash
git diff [base-branch]...HEAD
```

### 3.5 hooks.md

フック設定の指針を定めるファイルです。

#### フックタイプ

| フックタイプ | タイミング |
|------------|----------|
| `PreToolUse` | ツール実行前 |
| `PostToolUse` | ツール実行後 |
| `Stop` | セッション終了時 |

#### TodoWrite統合
- フックと `TodoWrite` を連携させることで、進捗追跡と実装ステップの可視化が可能
- 作業状況をリアルタイムで確認できる

#### 注意事項
- 探索的作業（設計検討・実験）では、フックを一時的に**無効化**することを推奨
- フック内で `curl`・`wget`・`nc` などのネットワークコマンドを使用する場合はセキュリティレビューが必須

### 3.6 patterns.md

アーキテクチャパターンを定義するファイルです。

#### スケルトンプロジェクトパターン
新規プロジェクト開始時は、ゼロから作らず実績あるプロジェクトをベースにします。
1. GitHub検索でスケルトンを探す
2. 要件との適合度を評価
3. クローンして基盤として使用

#### Repositoryパターン
データアクセス層に一貫したインターフェースを適用します。

```
Repository interface:
- findAll()     # 全件取得
- findById(id)  # ID検索
- create(data)  # 作成
- update(id, data) # 更新
- delete(id)    # 削除
```

#### APIレスポンスエンベロープ構造
APIのレスポンスは必ず以下のエンベロープ形式で統一します。

```json
{
  "success": true,
  "data": { ... },
  "error": null,
  "meta": {
    "pagination": { ... }
  }
}
```

### 3.7 performance.md

パフォーマンス最適化とモデル選定戦略を定めるファイルです。

#### モデル選定戦略

| モデル | 主な用途 | コスト効率 |
|--------|---------|----------|
| **Haiku 4.5** | 軽量エージェント、単一ファイル編集 | Sonnet比3倍安価 |
| **Sonnet 4.6** | メイン開発作業（90%のタスク） | 最高コーディング品質 |
| **Opus 4.6** | 複雑なアーキテクチャ設計、セキュリティ分析 | 最深の推論能力 |

> **目安:** 通常の開発作業は Sonnet 4.6 で十分。設計フェーズや高度なセキュリティ分析では Opus 4.6 を使う。単純なファイル操作は Haiku 4.5 でコスト削減。

#### コンテキストウィンドウ管理
- コンテキストウィンドウの**残り20%** になったら大規模リファクタリングを避ける
- この状態での変更は品質低下リスクが高い

#### 拡張思考（Extended Thinking）
- `Option+T` / `Alt+T` でトグル
- 最大 **31,999トークン**まで利用可能
- 複雑な問題解決・設計検討時に有効

### 3.8 security.md

セキュリティ対策の必須チェックリストを定めるファイルです。

#### コミット前の8項目必須チェック

```
□ 1. ハードコードされたシークレット（パスワード・APIキー等）がないか
□ 2. ユーザー入力に適切なバリデーションがあるか
□ 3. SQLインジェクション対策が実施されているか
□ 4. XSS（クロスサイトスクリプティング）対策が実施されているか
□ 5. CSRF保護が実装されているか
□ 6. 認証・認可の検証が正しいか
□ 7. レート制限が実装されているか
□ 8. エラーメッセージが内部情報を漏洩していないか
```

#### セキュリティ問題発生時の対応プロトコル

```
1. 問題を発見したら即座に作業を停止
2. security-reviewer エージェントを呼び出す
3. CRITICAL 優先度として扱い、他の作業より優先
4. シークレット漏洩の場合はローテーション（無効化・再発行）を即時実施
```

### 3.9 testing.md

テスト方針とカバレッジ要件を定めるファイルです。

#### 最低カバレッジ要件

```
コードカバレッジ: 80%以上（必須・厳守）
```

#### 必須テスト種類

| テスト種類 | 対象 | 必須度 |
|----------|------|--------|
| **ユニットテスト** | 関数・クラス単体 | 必須 |
| **統合テスト** | モジュール間連携 | 必須 |
| **E2Eテスト** | ユーザーフロー全体 | 必須 |

#### TDDフロー

```
RED → GREEN → IMPROVE → カバレッジ確認

RED:     テストを書く（この時点で失敗することを確認）
GREEN:   テストが通る最小限の実装をする
IMPROVE: リファクタリングで品質を向上させる
確認:    カバレッジが80%以上であることを確認
```

## 4. 言語別ルール

言語固有のルールファイルは、`../common/` への相対パスで共通ルールを**継承**しながら、フレームワーク固有のパターンを追加定義します。

### 4.1 TypeScript

#### coding-style.md
- 対象ファイル: `**/*.ts`, `**/*.tsx`, `**/*.js`, `**/*.jsx`
- スプレッド演算子でイミュータブル更新（`{...obj, key: newValue}`）
- 非同期処理: `async/await` + `try-catch` パターン必須
- バリデーション: **Zod** を使用（型安全なスキーマ検証）
- `console.log` は本番コードで禁止（ロギングライブラリを使用）

#### hooks.md（TypeScript固有の自動チェック）
- **PostToolUse（Edit時）:**
  - Prettier または Biome で自動整形
  - TypeScript 型チェック（`tsc --noEmit`）
  - `console.log` 検出時に警告
- **Stop（セッション終了時）:**
  - 変更されたすべてのファイルに対して `console.log` 全体監査

#### patterns.md
- APIレスポンス: ジェネリック型パラメータ付きインターフェース `ApiResponse<T>`
- カスタムHooks: `useDebounce` などの合成パターン
- Repositoryパターン: `Promise<T>` を返す非同期メソッド

#### testing.md
- E2Eテスト: **Playwright** を使用
- `e2e-runner` エージェントで自動実行をサポート

## 5. 多層継承構造

everything-claude-code のルール設計は**多層継承**アーキテクチャを採用しています。

```
適用優先順位（高 → 低）

┌─────────────────────────────────┐
│  言語固有ルール                    │  ← 最高優先度
│  (typescript/, python/, etc.)   │     フレームワーク固有のパターン
├─────────────────────────────────┤
│  共通ルール                       │  ← 基盤
│  (common/)                      │     言語非依存の原則
└─────────────────────────────────┘
```

#### 継承の仕組み

言語固有ファイルは、共通ルールを `../common/` への相対パス参照で取り込みます。

```markdown
<!-- typescript/coding-style.md の例 -->
@../common/coding-style.md

# TypeScript 固有の追加ルール
...
```

このアーキテクチャにより：
- **共通原則の一元管理:** common/ を更新すれば全言語に反映
- **言語固有の柔軟性:** 各言語のベストプラクティスを個別に定義
- **DRY原則の実現:** 重複定義をなくし保守性を向上

## 6. 自作ルールの追加方法

プロジェクト固有のルールを追加する手順を説明します。

### Step 1: ルールファイルの作成

既存のファイル命名規則に従い、適切なディレクトリに配置します。

```bash
# 共通ルールに追加する場合
touch rules/common/my-custom-rule.md

# 言語固有ルールに追加する場合
touch rules/typescript/my-custom-rule.md
```

### Step 2: ファイルの基本構造

```markdown
# [ルール名]

## 概要
このルールが解決する問題と目的を記述します。

## 原則
- 原則1: ...
- 原則2: ...

## 具体例

### 良い例
```
// ✅ 推奨するコード
```

### 悪い例
```
// ❌ 避けるべきコード
```

## チェックリスト
- [ ] 確認項目1
- [ ] 確認項目2
```

### Step 3: CLAUDE.md からインポート

作成したルールをプロジェクトの CLAUDE.md に追加します。

```markdown
<!-- CLAUDE.md -->
@rules/common/my-custom-rule.md
@rules/typescript/my-custom-rule.md
```

### Step 4: 既存ルールとの整合性確認

新しいルールを追加する前に、以下を確認してください。

```
□ common/ の既存ルールと矛盾していないか
□ 言語固有ルールと重複していないか
□ チーム全員が理解・遵守できる内容か
□ 自動チェック（フック等）で検証できるか
```

### Step 5: フックによる自動適用（推奨）

ルールを人的チェックだけに依存させず、フックで自動検証することを推奨します。

```json
// hooks.json への追加例
{
  "PostToolUse": [
    {
      "matcher": "Edit",
      "hooks": [
        {
          "type": "command",
          "command": "my-custom-lint-script.sh"
        }
      ]
    }
  ]
}
```
