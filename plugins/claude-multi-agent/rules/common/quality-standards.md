# 品質基準

## テスト

- **最低カバレッジ**: 80%（ステートメントカバレッジ）
- **テスト種別**: Unit + Integration + E2E をすべて用意する

### TDD（テスト駆動開発）— T-wada流

#### 基本サイクル: Red → Green → Refactor
1. **Red**: まず失敗するテストを1つだけ書く。コンパイルエラーも「Red」に含む
2. **Green**: そのテストを通す最小限のコードを書く。ここでは「正しい実装」ではなく「動く実装」を優先する
3. **Refactor**: テストが通った状態を維持しながらコードを改善する。重複除去・命名改善・構造整理を行う

#### 重要な原則
- **一度に1つのテスト**: 複数のテストを同時に追加しない。1つずつ確実に進める
- **仮実装（Fake It）**: 最初はハードコードした値を返してでもテストを通す。そこから段階的に本物の実装へ進化させる
- **三角測量（Triangulation）**: 1つのテストだけでは実装が確定しない場合、別の具体例をテストとして追加し、一般化を促す
- **明白な実装（Obvious Implementation）**: 実装が自明な場合はそのまま書いてよいが、テストが失敗したら仮実装に戻る
- **小さいステップ**: 不安な時ほどステップを小さくする。自信がある時はステップを大きくしてよい
- **テストの書き順**: テストは「Arrange（準備）→ Act（実行）→ Assert（検証）」の順で構成するが、書く順序は逆（Assert → Act → Arrange）で考えると意図が明確になる

#### やってはいけないこと
- テストを書かずに実装コードを先に書く → **実装コードの前に必ずテストを書く**
- Redを確認せずにGreenへ進む → **テストが失敗することを確認してからGreenへ進む**（テストが最初から通る場合、そのテストは価値がない可能性がある）
- Refactorフェーズを飛ばす → **Greenの後は必ずRefactorフェーズを実施する**
- テストコードの品質を軽視する → **テストもプロダクションコードと同等の品質を保つ**

## コードレビュー重要度分類

- **CRITICAL**（セキュリティ・データ破壊）: マージ禁止、即時修正必須
- **HIGH**（バグ・品質）: 修正後にマージ可
- **MEDIUM**（パフォーマンス・保守性）: 次回スプリントで対応可
- **LOW**（スタイル・好み）: 任意対応

## ビルド検証

タスク完了前に、プロジェクトのビルド・型チェックを実行し、自分の変更に起因するエラーがないことを確認すること。

### 必須手順
- プロジェクトの `package.json` に定義されたビルドコマンド（`build`, `typecheck`, `check` 等）を確認し実行する
- ビルドコマンドが不明な場合は `package.json` の `scripts` セクションを読んで適切なコマンドを特定する
- 自分の変更に起因するエラーは必ず修正してから完了報告する
- 既存のエラー（自分の変更前から存在するもの）は、共有ディレクトリに報告してチームに通知する

## Lintエラー修正

Lintエラー（ESLint, Biome, TypeScript等）を修正する際、コメントによるエラー抑制は**禁止**。

### 禁止するコメント例
- `// eslint-disable-next-line` / `// eslint-disable` / `/* eslint-disable */`
- `// @ts-ignore` / `// @ts-expect-error`
- `// biome-ignore`
- その他、lint警告・エラーを無視するためのコメント全般

### 必須対応
- **必ずコードを修正してエラーの根本原因を解消すること**
- コメントでエラーを黙らせる対応は認めない
